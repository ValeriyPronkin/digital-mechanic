# «Load failed» голоса в Safari — разбор 26.11

**Симптом (человек, iPhone, LTE, стенд с ветки `14-voice`):** голосовой вопрос → «Load failed», запрос оборвался без ответа.

**Журнал контейнера:** недоступен. Ревизии пишут в журнал каталога по умолчанию (`log_options.folder_id`),
но группы `default` в каталоге нет («failed to find LogGroup with name "default"»), список групп — `Unavailable`.
Записей контейнера нет ни за какой период → вопрос человеку (создать группу журнала / роль `logging.reader`).

**Воспроизведение с Mac** (стенд через VPN Happ), `curl -w` по фазам, 10 запросов `/health`:

| Фаза | Время |
|---|---|
| TCP | 0,004–0,006 с (соединение принимает локальный туннель) |
| TLS-рукопожатие | 0,24–1,1 с в 4 из 10; **16,2 / 16,3 / 16,3 / 32,8 / 48,5 с** в 5 из 10; обрыв `SSL_ERROR_SYSCALL` через 83 с — 1 из 10 |
| Ответ сервера после TLS | 0,15–5,4 с |

**Тот же замер из GitHub Actions** (run 45834248080): 20 из 20 — TLS 0,26–0,28 с, весь запрос 0,41–0,65 с.

**Экземпляры** (`/health` → `instance`): импорт 1,5–1,8 с, скачивание индекса 0,75–1,04 с; долгие запросы приходят
и на давно живой экземпляр (uptime 30–50 с) — холодный старт контейнера ни при чём.

**Вывод:** время теряется в TLS-рукопожатии на пути клиент → Yandex Cloud (шаг ~16 с — повторы пакетов),
не в сервисе. WebKit обрывает загрузку после 60 с → «Load failed». Голосовой путь — три запроса подряд
(распознавание → чат → озвучка), у него больше шансов попасть на зависшее рукопожатие.

**Что сделано в коде:** страница повторяет запрос при сетевом обрыве: распознавание и озвучка — свой таймаут 25 с
и до 3 попыток, чат — 1 повтор (без своего таймаута: ответ модели бывает долгим); механик видит
«Связь плохая — повторяю…», после последней попытки — «Связь со стендом оборвалась…». Ответ сервера с ошибкой
не повторяется. `scripts/stand_voice.py` / флаг `voice_live` — голос на стенде как со страницы, с временем шагов.

**Не проверено:** телефон без VPN по LTE — на нём путь до Yandex Cloud свой; нужна повторная проверка человеком.
